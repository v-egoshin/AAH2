# Техническое задание: новый репозиторий AAH2 с минимальным core и подключаемыми модулями

Дата: 2026-06-03

---

## 1. Контекст

Необходимо создать **новый репозиторий** для следующей итерации AAH2.  
Текущий репозиторий используется **только как справочный материал**:

- для анализа удачных решений;
- для анализа неудачных архитектурных мест;
- для переноса бизнес-смыслов и API-идей;
- для проверки, какие сущности и сценарии реально нужны.

Текущий репозиторий **не** является базой для постепенного рефакторинга.  
Новая система проектируется как самостоятельный продукт с новой структурой кода.

---

## 2. Цель

Построить новую кодовую базу AAH2 с архитектурой:

- минимальный, жёстко ограниченный `core`;
- отдельный `ingest/inbox` слой;
- подключаемые `capability modules`;
- отдельные `projections`;
- явный runtime bootstrap и capability registry.

Главная цель:

**избежать повторного появления монолита, в котором весь домен, API и workflow зашиты в единый store и единый набор роутов.**

---

## 3. Основные принципы

### 3.1. Новый репозиторий, а не рефакторинг старого

Нельзя:

- переносить старую структуру каталогов как есть;
- копировать `god store`;
- повторять модель, где все домены живут в одном классе;
- держать все роуты всегда включёнными.

Можно:

- использовать текущий репозиторий как справочник по сущностям и сценариям;
- брать оттуда примеры payload, API, enums, тестовых сценариев;
- использовать отдельные идеи и названия, но не повторять архитектурный каркас.

### 3.2. Сначала core, потом остальное

Новая кодовая база должна собираться слоями:

1. `core`
2. `ingest/inbox`
3. `capability modules`
4. `projections`

### 3.3. Модульность не декларативная, а реальная

Подключаемый модуль должен реально:

- регистрироваться отдельно;
- иметь собственный bootstrap;
- иметь собственный service/repository слой;
- иметь собственные маршруты;
- быть отключаемым через runtime config;
- не ломать запуск системы при выключении.

---

## 4. Границы домена

### 4.1. Что входит в core

В core входят только:

- `Assessment`
- `Asset`
- `Object`
- `Audit`
- `DomainError`

### 4.2. Что не входит в core

#### Ingest / Inbox layer

- `ImportBatch`
- `Candidate`

#### Capability modules

- `Relation`
- `Mark`
- `Check`
- `Case`
- `Finding`
- `Evidence`

#### Projections

- `review_context`
- `coverage`

## 5. Смысл core-сущностей

### `Assessment`

Root context всей системы.

Нужен как:

- контейнер анализа;
- корневая точка изоляции данных;
- общий контекст для assets, objects и модулей;
- единица работы пользователя/агента.

### `Asset`

Цель анализа.

Примеры:

- репозиторий;
- сервис;
- URL;
- бинарь;
- пакет;
- образ.

### `Object`

Базовый атом предметной модели.

Примеры:

- файл;
- функция;
- endpoint;
- callsite;
- handler;
- query fragment;
- symbol;
- route.

### `Audit`

Единый системный след.

Нужен для:

- наблюдаемости;
- трассировки действий;
- отладки automation;
- фиксации действий агентов и людей.

### `DomainError`

Единый контракт ошибок домена.

Нужен для:

- согласованного API;
- единообразных исключений;
- предсказуемой обработки ошибок клиентами и автоматизацией.

## 8. Требования к архитектуре

### 8.1. Runtime bootstrap

Система должна запускаться через единый bootstrap:

- создание `AppContext`;
- регистрация core;
- регистрация ingest;
- регистрация включённых модулей;
- публикация capabilities.

Роуты не должны регистрироваться вручную в `main.py` длинным списком.

### 8.2. `AppContext`

Должен существовать объект runtime-контекста, содержащий:

- settings;
- repositories;
- services;
- capability registry;
- accept registry;
- projection registry.

### 8.3. Module registry

Все подключаемые модули должны включаться через единый registry.

Примерно:

- `graph`
- `marks`
- `checks`
- `cases`
- `findings`
- `evidence`
- `review_context`
- `coverage`

### 8.4. Capabilities endpoint

API должен отдавать текущую конфигурацию runtime.

Минимально:

```json
{
  "modules": ["graph", "marks"],
  "core": true,
  "ingest": true,
  "projections": ["review_context"]
}
```

### 9.2. `Asset`

Минимальные операции:

### 9.4. `Audit`

Минимальные операции:

- выброс доменной ошибки;
- преобразование в HTTP-ответ;
- единый JSON-формат ошибки.

---

## 10. Требования к ingest / inbox

Слой ingest должен жить отдельно от core.

Он должен включать:

- импорт батчей;
- создание кандидатов;
- dedupe;
- triage;
- accept/reject/merge;
- работу через `AcceptRegistry`.

Ключевое требование:

**ingest не должен содержать зашитую логику всех будущих доменов внутри одного метода.**

То есть `accept_candidate()` не должен знать всё про:

- marks;
- checks;
- cases;
- findings.

Он должен уметь только:

- взять тип кандидата;
- найти соответствующий handler;
- делегировать обработку.

---

## 11. Требования к подключаемым модулям

Каждый модуль обязан иметь одинаковый контракт.

Минимальная структура модуля:

```text
modules/<module_name>/
├── bootstrap.py
├── schemas.py
├── repository.py
├── service.py
├── routes.py
└── handlers/
```

### Что делает модуль

Модуль должен уметь:

1. зарегистрировать свои repositories;
2. зарегистрировать свои services;
3. подключить routes;
4. зарегистрировать candidate handlers, если нужно;
5. объявить свою capability;
6. иметь собственные тесты;
7. иметь свои миграции схемы данных.

### Что модуль не должен делать

Модуль не должен:

- менять bootstrap core;
- требовать переписывания других модулей;
- ломать запуск системы при отключении;
- зашивать предположение, что все другие модули уже активны.

---

## 12. Требования к projections

`review_context` и `coverage` должны быть реализованы как read-model слои.

Они:

- не являются корневыми доменными агрегатами;
- не должны определять форму core;
- должны уметь деградировать, если часть модулей выключена.

Пример:

- если нет `checks`, `coverage` не считает check-метрики;
- если нет `findings`, `coverage` не показывает finding-секцию;
- если нет `marks`, `review_context` не строит mark-контекст.

---

## 13. Требования к данным и миграциям

### 13.1. Общий подход

Миграции БД должны быть отделены от runtime-активации модулей.

Это значит:

1. схема данных может быть уже накатана;
2. код модуля может быть уже задеплоен;
3. модуль может оставаться выключенным;
4. capability становится доступной только после runtime-включения.

### 13.2. Правила

- core-таблицы идут в базовом наборе миграций;
- ingest-таблицы идут отдельным набором;
- каждый capability module добавляет только свои таблицы и индексы;
- projections могут использовать отдельные projection tables или кеши;
- выключение модуля не должно удалять таблицы автоматически.

### 13.3. Rollout нового модуля

Правильная последовательность:

1. добавить миграцию схемы;
2. выкатить код модуля;
3. при необходимости выполнить backfill;
4. включить модуль через конфиг;
5. убедиться, что `/api/capabilities` отражает включение.

---

## 14. Требования к конфигурации

Должна быть настройка вида:

```bash
AAH2_MODULES=graph,marks,checks
STORE_BACKEND=sql
```

Правила:

- core всегда активен;
- ingest всегда активен;
- модули перечисляются явно;
- projections включаются явно;
- клиенты должны опираться на `/api/capabilities`, а не на предположение, что всё всегда включено.

- assessments
- assets

### 15.2. Ingest API

Обязательные группы:

- imports
- candidates

Должен подключаться только при включённом модуле.

## 17. Нефункциональные требования

### 17.1. Расширяемость

Добавление нового capability-модуля не должно требовать:

- переписывания core;
- переписывания ingest;
- переписывания существующих модулей.

### 17.2. Прозрачность

Система должна явно показывать, какие модули активны.

### 17.3. Предсказуемость

Поведение отключённого модуля должно быть очевидным:

- routes отсутствуют или недоступны;
- handler не зарегистрирован;
- projection не пытается использовать его данные.

### 17.4. Наблюдаемость

Ключевые операции должны оставлять audit trace.

## 19. Критерии приёмки

ТЗ считается выполненным, если:

1. существует новый отдельный репозиторий;
2. core реализован как отдельный слой;
3. ingest реализован как отдельный слой;
4. модуль `graph` можно включить и выключить конфигом;
5. минимум один аналитический модуль можно подключить без изменения core;
6. `/api/capabilities` отражает реальные активные capability;
7. projections корректно деградируют при отключённых модулях;
8. нет единого store-класса, который знает весь домен;
9. нет безусловной регистрации всех роутов сразу;
10. текущий репозиторий использован только как reference, а не как архитектурная основа.

---

## 20. Ожидаемый результат

На выходе должен получиться новый AAH2-репозиторий, в котором:

- core минимален и стабилен;
- ingest изолирован;
- новые capability добавляются как модули;
- projections не раздувают домен;
- rollout функциональности управляется конфигом и capability registry;
- архитектура изначально рассчитана на инкрементальное развитие без возврата к монолитному store.
